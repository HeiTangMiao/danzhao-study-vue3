## 第 1 部分：S3 部署侧核实（3 条命令）

### 背景：这里藏着一个我抓到的陷阱

Tauri 的 `.env.tauri` 注入的 API 基址是 **`https://520305.top/api`**（**带 `/api`**），而 `/api` 在 nginx 上是**反代给 Fastify 后端**的路由前缀。如果远程内容被部署到 `/api` 下，请求会被转给后端、返回 **404** —— 不是网络错、也不是 CSP 拦截，是**最难排查的那一类失败**。

所以 S2 的 `contentRootFrom()` 在绝对模式下取的是 `new URL(API_BASE).origin`（= `https://520305.top`）再拼 `/content-remote/`。**本部分就是验证这个代码口径与服务器实际落点一致。**

### 1.1 正向：确认正确地址可达

```bash
curl -sS -o /dev/null -w "HTTP %{http_code}\n" \
  https://520305.top/content-remote/manifest.json
```

**预期**：`HTTP 200`

### 1.2 反向：确认它**不在** `/api` 下（这条同样重要）

```bash
curl -sS -o /dev/null -w "HTTP %{http_code}\n" \
  https://520305.top/api/content-remote/manifest.json
```

**预期**：`HTTP 404`

> 若这条返回 **200**，说明服务器把内容放在了 `/api` 下，与代码口径冲突 → **把结果告诉我**，我来改 `contentRootFrom()`。（改起来很快，但必须先确认事实。）

### 1.3 看内容对不对

```bash
curl -sS https://520305.top/content-remote/manifest.json | python3 -c "
import json,sys
m=json.load(sys.stdin)
print('schemaVersion :', m['schemaVersion'])
print('contentVersion:', m['contentVersion'])
print('单元数        :', len(m['units']))
print('页合计        :', sum(u['count'] for u in m['units'].values()))
print('search/practice:', m['search'], m['practice'])
print('sitePatch     :', m['sitePatch'])
"
```

**预期**（基于当前内容状态）：

| 字段 | 预期值 |
|---|---|
| `schemaVersion` | `1` |
| `contentVersion` | `1` |
| 单元数 | **27** |
| 页合计 | **183** |
| `search` / `practice` | `null` / `null`（P-S07 预留键位，本阶段不产出） |
| `sitePatch` | `{"units": {}, "fileMetaUpdates": []}`（B1 恒空） |

> 若**页合计不是 183**：通常是服务器上的快照是旧的（发布时机问题），不是代码问题 —— 重跑 `npm run build:content-remote` 再 rsync 即可。

### 失败分诊表

| 现象 | 属于哪一层 |
|---|---|
| 1.1 返回 404 | 快照**从未部署**到服务器（S3 还没做）→ 需先 `npm run build:content-remote` 再 rsync |
| 1.1 和 1.2 都 404 | 同上，快照未部署 |
| 1.1 返回 403 / 证书错误 | nginx 配置或证书问题，**非应用代码** |
| 1.2 返回 200 且 1.1 返回 404 | **口径冲突**（内容在 `/api` 下）→ 告诉我 |

## 第 2 部分：Tauri 桌面端真机验证

### 准备

```bash
npm ci
npm run tauri:build
```

（`tauri:build` 会**自动**清理残留的 `public/content-remote/` —— 那是本地打包特有的边界，GitHub Release 不受影响。想更快就用 `npm run tauri dev` 跑开发模式。）

> ⚠️ 注意：`npm run build` 在 WorkBuddy 沙箱内会被 safe-delete 守卫拦截（递归清理超 50 项阈值），**请在沙箱外执行**。

### 2.1 绝对地址可达（且只在启动时拉一次）

- 打开应用 → 开 DevTools → 网络面板 → 进入任意内容页
- 找对 `https://520305.top/content-remote/manifest.json` 的请求

**预期**：状态 **200**，且**只在应用启动后发起一次**（`startBackgroundRefresh()`，按 P-S14 一次会话只触发一次）。

> ⚠️ **关键反例**：如果在**翻页 / 进页时**反复看到这个请求 → 说明 `loadPage` 里混进了网络 `await`，会劣化 `UnitView.vue:551` 那条 400ms 翻页竞速。这正是 P-S11「网络不进关键路径」的全部理由 —— **这类回归测试全绿也发现不了**（用例全过，只是翻页变卡）。发现就告诉我。

### 2.2 无 CSP violation

- 控制台过滤 `CSP`

**预期**：**零** violation。

若出现 `connect-src` 相关拦截 → 服务器域名不在 CSP 白名单（`src-tauri/tauri.conf.json`）→ 告诉我，我来加。

### 2.3 断网回退内置（"永不变砖"的最终确认）

- 应用运行中，断开网络（拔网线 / 关 Wi-Fi / 飞行模式）
- 重新进入若干内容页，并翻页

**预期**：**页面照常显示内容**（走内置兜底），**不白屏、不报错、不出现空 blocks**。

这条是"轨道 A 零回归"红线的最终落地确认。

### 2.4（可选）验证远程更新真的生效

这一条会**实证一个我反复提醒的操作陷阱**，建议做：

1. 把 `src/content/contentManifest.js` 的 `CONTENT_VERSION` 改成 `2`
2. 重跑 `npm run build:content-remote`，部署到服务器
3. 重启桌面应用 → 观察是否拉到 v2 并应用

**预期**：应用拉到 v2 并更新缓存。

> ⚠️ **这条要证明的陷阱**：`CONTENT_VERSION` 与 release tag **完全解耦**，是手填的单调号。如果内容改了但版本号没 +1，客户端的 `isNewer()` 会返回 false → **永远拉不到新内容，而且不报错**。正确顺序永远是：**改内容 → `CONTENT_VERSION` +1 → 构建 → 部署**。
