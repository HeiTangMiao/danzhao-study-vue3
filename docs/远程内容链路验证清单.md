## 第 1 部分：S3 部署侧核实（3 条命令）

### 背景：这里藏着一个我抓到的陷阱

Tauri 的 `.env.tauri` 注入的 API 基址是 **`https://520305.top/api`**（**带 `/api`**），而 `/api` 在 nginx 上是**反代给 Fastify 后端**的路由前缀。如果远程内容被部署到 `/api` 下，请求会被转给后端、返回 **404** —— 不是网络错、也不是 CSP 拦截，是**最难排查的那一类失败**。

所以 S2 的 `contentRootFrom()` 在绝对模式下取的是 `new URL(API_BASE).origin`（= `https://520305.top`）再拼 `/content-remote/`。**本部分就是验证这个代码口径与服务器实际落点一致。**

### ⚠️ 先读这条：光看 `HTTP 200` 会被骗

本服务器的 nginx 配了 **SPA fallback**——**任何找不到的路径都返回 `200` + `index.html`**（实测对照：`/definitely-not-exist-xyz.json` 也返回 `200 text/html`）。

所以判据**必须**带上 `content-type`：

| 真实情况 | HTTP | content-type |
|---|---|---|
| 文件存在 | 200 | **`application/json`**（或 `image/x-icon` 等真实类型） |
| 文件不存在（被 fallback 顶替） | **200** ⚠️ | **`text/html`** |

**「200 + text/html」= 文件不存在**，不要误判为成功。

### 1.1 正向：确认正确地址可达

```bash
curl -sS -o /dev/null -w "HTTP %{http_code}  content-type=%{content_type}\n" \
  https://520305.top/content-remote/manifest.json
```

**预期**：`HTTP 200  content-type=application/json`
（若为 `text/html` → **快照尚未部署到服务器**，属 S3 未做，不是代码问题）

### 1.2 反向：确认它**不在** `/api` 下（这条同样重要）

```bash
curl -sS -o /dev/null -w "HTTP %{http_code}  content-type=%{content_type}\n" \
  https://520305.top/api/content-remote/manifest.json
```

**预期**：`HTTP 404`（`/api` 走 Fastify 代理，没有 SPA fallback，所以这里能真实反映"不存在"）
> 若返回 200 → 内容被部署到了 `/api` 下，与代码口径冲突，告诉我。

> 若这条返回 **200**，说明服务器把内容放在了 `/api` 下，与代码口径冲突 → **把结果告诉我**，我来改 `contentRootFrom()`。（改起来很快，但必须先确认事实。）
