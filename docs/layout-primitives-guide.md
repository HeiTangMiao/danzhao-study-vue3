# 布局原语作者使用说明（layout primitives guide）

面向**写内容的人**（`src/content/**/*.js` 的作者），不是面向改渲染代码的人。

本文只讲三件事：什么时候用哪个原语、`props` 怎么填、嵌套怎么把握。取值域一律以
`schema/content-schema.json` 的 `definitions.layoutKind` 与 `definitions.layoutProps` 为唯一真相源；
本文是它的中文注解，两者冲突时以 schema 为准（`npm run validate:content` 也是按 schema 判的）。

---

## 一、布局区块长什么样

布局原语与普通区块**共用同一个 `type` 键**，不引第二个 `kind` 键 —— 这样校验器与注册表只需要认识
`type` 一处入口，不必再维护一套并行的判别逻辑。写法：

```js
{
  type: 'layout',      // 固定值，表明这是一个布局容器
  as: 'grid',          // 必填：用哪个原语（取值域见第二节）
  title: '两组对照',    // 可选：给了就渲染一个小标题，不给就不渲染
  props: { cols: 2 },  // 可选：原语参数（各原语允许的键见第三节）
  children: [ /* 区块或嵌套的 layout */ ]  // 必填：子内容，可为普通区块，也可再嵌 layout
}
```

三个字段的分工：

- `as` 决定**怎么排**，`children` 决定**排什么**，`props` 决定**排的细节**。
- `children` 里的元素和顶层 `blocks` 数组里的元素是**同一种东西**：既可以是 `knowledge`、`quiz`
  这类普通区块，也可以是另一个 `type: 'layout'`（即布局可以嵌套布局）。
- `children` 建议非空。空布局不报错，但渲染出一个没有内容的空壳容器没有任何意义，属于内容缺陷。

## 二、六个原语：先选对，再填参

| 原语 | 一句话定位 | 什么时候用 | 默认行为 |
|---|---|---|---|
| `grid` | 让 children 等宽成网格 | 并列的同类项（如多组小结、多个小测点），彼此无主次 | 2 列；容器不够宽时自动降为单列 |
| `stack` | 把 children 纵向依次堆叠 | 需要给「刻意的一列」一个显式身份，并单独控制间距 | 纵向一列 |
| `split` | 主次分栏 | 一组内容有明确的主/次关系，次要内容不该打断主语流 | 左右各半；容器不够宽时降为单列 |
| `hero` | 首屏 / 章节强调区 | 一页开头的引导段、或某一章的题眼 | 单列左对齐，无强调底色 |
| `bleed` | 出血，突破阅读版心 | 表格、图、代码这类「窄版心里放不下」的宽内容 | 两侧出血，幅度 wide |
| `rail` | 侧轨 + 主内容 | 主内容旁边有一路辅助信息（导航、摘要、要点索引） | 侧轨在左、宽度 sm、不吸顶 |

**选型要点（为什么这样分）**：

- `grid` 与 `split` 都是横向排列，区别在**均分还是分主次**。cols=2 的 grid 和 ratio=1:1 的 split
  视觉上可能相近，但语义不同：grid 说的是「这些地位一样」，split 说的是「前者为主、后者为辅」。
  选错不影响渲染，只影响后来人读懂结构 —— 但那是内容可维护性的一部分。
- `stack` 存在的价值不是「能纵向排列」（纵向本就是阅读流默认节奏），而是**让这种刻意安排有显式身份**。
  如果只是顺次放区块，直接平铺即可，不必包一层 stack。
- `hero` 的 `align` 默认 `start` 而非 `center`，是因为长文居中会显著降低可读性；
  只有短句、标题这类内容才考虑 `center`。
- `bleed` 的安全边界由样式侧兜底：**容器本身不够宽时自动回落为零出血**，不会把内容顶出可视区。
  所以用它不需要作者自己判断屏宽。
- `rail` 的契约是「**第一个 child 就是侧轨**」。窄容器降为单列时，侧轨因为排在第一个，会自然落到
  正文之前 —— 这是刻意的降级顺序，不是 bug。因此侧轨内容要按「先出现也读得通」来写。

## 三、各原语参数（照 schema 抄，勿凭记忆）

下表逐字对应 `schema/content-schema.json` 的 `definitions.layoutProps`。
**未知的键会被校验器直接拒绝**（不是忽略），所以只填下表列出的键。

### grid

| 键 | 取值域 | 默认 | 含义 |
|---|---|---|---|
| `cols` | `2` `3` `4` | `2` | 容器足够宽时的列数 |
| `gap` | `'normal'` `'tight'` `'loose'` | `'normal'` | 间距档 |

```js
{
  type: 'layout',
  as: 'grid',
  title: '三组对照练习',
  props: { cols: 3, gap: 'tight' },
  children: [
    { type: 'tip', text: '第一组要点' },
    { type: 'tip', text: '第二组要点' },
    { type: 'tip', text: '第三组要点' }
  ]
}
```

### stack

| 键 | 取值域 | 默认 | 含义 |
|---|---|---|---|
| `gap` | `'normal'` `'tight'` `'loose'` | `'normal'` | 纵向间距档 |

```js
{
  type: 'layout',
  as: 'stack',
  props: { gap: 'loose' },
  children: [
    { type: 'knowledge', paragraphs: ['本节的第一个知识点'] },
    { type: 'knowledge', paragraphs: ['本节的第二个知识点'] }
  ]
}
```

### split

| 键 | 取值域 | 默认 | 含义 |
|---|---|---|---|
| `ratio` | `'1:1'` `'1:2'` `'2:1'` `'1:3'` `'3:1'` | `'1:1'` | 开始侧 : 结束侧的列宽比 |
| `gap` | `'normal'` `'tight'` `'loose'` | `'normal'` | 分栏间隙档 |

排布契约：**前两个 child 分列左右**（前者在起始侧、后者在结束侧）。第 3 个及以后的 child
**按行顺排**（CSS 网格默认流：先填满一行再换下一行），即第 3 个落在第二行的**起始侧**（主侧），
第 4 个落在第二行的结束侧，依此类推 —— 多出来的主内容继续接在主侧下方，符合「主次分栏」的语义；
且不会静默丢弃内容。

> 口径说明（2026-10-07 实测校正）：本文档早前写的是「第 3 个起排在结束侧之后」，与实现（CSS 网格默认行流）
> 不符。经实测确认实现行为是**按行顺排**，且该行为更贴合主次语义，故改文档而非改实现。

```js
{
  type: 'layout',
  as: 'split',
  props: { ratio: '1:2' },
  children: [
    { type: 'objectives', items: ['读懂题意', '选对方法'] },
    { type: 'example', items: [{ question: '题干', solution: '解答' }] }
  ]
}
```

### hero

| 键 | 取值域 | 默认 | 含义 |
|---|---|---|---|
| `align` | `'start'` `'center'` | `'start'` | 内容水平对齐 |
| `tone` | `'plain'` `'accent'` | `'plain'` | `accent` 给整块加一层极浅强调底色 |

`accent` 只加**极浅底色**，不做大面积渐变 —— 阅读页要克制，强调靠位置与留白，不靠重色块。

```js
{
  type: 'layout',
  as: 'hero',
  props: { align: 'start', tone: 'accent' },
  children: [
    { type: 'tip', text: '本章要解决的问题：如何由三视图还原几何体' }
  ]
}
```

### bleed

| 键 | 取值域 | 默认 | 含义 |
|---|---|---|---|
| `side` | `'start'` `'end'` `'both'` | `'both'` | 出血方向 |
| `width` | `'wide'` `'full'` | `'wide'` | 出血幅度 |

```js
{
  type: 'layout',
  as: 'bleed',
  props: { side: 'both', width: 'wide' },
  children: [
    { type: 'table', headers: ['几何体', '结构特征'], rows: [['棱柱', '两底面平行且全等']] }
  ]
}
```

### rail

| 键 | 取值域 | 默认 | 含义 |
|---|---|---|---|
| `side` | `'start'` `'end'` | `'start'` | 侧轨在左还是在右 |
| `width` | `'sm'` `'md'` | `'sm'` | 侧轨宽度档 |
| `sticky` | `true` `false` | `false` | 侧轨是否吸顶 |
| `gap` | `'normal'` `'tight'` `'loose'` | `'normal'` | 侧轨与主内容的间隙档 |

```js
{
  type: 'layout',
  as: 'rail',
  props: { side: 'start', width: 'sm', sticky: true },
  children: [
    { type: 'summary', points: ['要点一', '要点二'] },   // 第一个 child 是侧轨
    { type: 'knowledge', paragraphs: ['主内容正文……'] }  // 其余是主内容
  ]
}
```

## 四、嵌套建议

布局可以嵌套布局，但嵌套是**为了表达真实的层级关系**，不是为了凑版式。

- 常见且合理的组合：`split` 的一侧放一个 `stack`（主次分栏里的次侧纵向罗列几条要点）。
- 不推荐：为了「看起来整齐」把一堆无关区块塞进同一个 `grid`；这会让人误以为它们是一组。
- 嵌套层数越深，内容越难读、越难改。**两层以内能表达清楚的，不要用三层。**

**深度硬上限：8 层**（代码常量 `MAX_LAYOUT_DEPTH`，见 `src/utils/validateBlock.js`）。
深度语义：顶层 layout 深度为 0，它的子 layout 深度为 1，依此类推；达到 8 即被拒绝，
报错为「布局嵌套超过上限 8 层」。超过上限不是「渲染变慢」这种软问题，而是**内容直接校验失败**，
所以不要贴着上限写。

## 五、三条必须遵守的作者约束

### 1. 取值域照 schema 抄，不要凭记忆

`as` 只能是 `grid` / `stack` / `split` / `hero` / `bleed` / `rail` 六个；各原语的 `props` 键与取值域
见第三节。这两份清单的唯一真相源是 `schema/content-schema.json` 的 `definitions.layoutKind` 与
`definitions.layoutProps`。

**`as` 写错**：渲染层会显示「未知布局原语」占位，不会静默变空白（这是刻意的降级策略，让错误看得见）。
**`props` 键写错或取值越界**：校验器报错。

提交前跑一次 `npm run validate:content`，它是 Node 侧关卡，与浏览器编辑器用的是同一份规则。

### 2. 嵌套深度上限 8

见第四节。上限存在的理由是防止异常内容把校验与渲染开销拖爆 —— 所以它是硬失败，不是警告。

### 3. 不要用 layout 去模拟已有区块

已经存在的容器型区块**继续有效，不要用 layout 重写它们**：

- `columns`（多列并列）
- `group`（松散的区块分组）

layout 是**新增**的一层表达能力，不是对既有容器类型的替换。用 layout 去重新实现 columns/group
只会让同一件事出现两种写法，后来人不知道该跟哪一种。存量 139 个内容页在这件事上不需要任何改动。

同理，不要用 layout 去包装「本来依次平铺就行」的区块 —— 那种包装只增加了一层无意义的缩进层级。

## 六、与其他层的边界（作者不需要管，但知道有好处）

- 布局原语**只负责排布**，不负责内容语义。区块内部长什么样，由各区块组件决定。
- 样式集中在本层自己的样式文件里（`src/assets/css/layouts.css`，由分发器引入），布局层可独立上线，
  引入或移除这一层不会牵动全局样式入口。
- 原语之间的组合是正交的：原语不认识具体区块类型，区块也不感知自己被放在哪个原语里。
  这也是「换个排布不用改内容、换个内容不用改排布」的原因。
