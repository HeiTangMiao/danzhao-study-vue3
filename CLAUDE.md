# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project at a glance

**浙江单招单考学习打卡** (`danzhao-study-vue3`) — content-driven study app for Zhejiang 单招 candidates covering 数学 / 语文 / 计算机. Ships as Vue 3 web + Tauri 2 desktop + Android APK. Content is data files rendered by schema-driven components; learning records live in IndexedDB and are optionally synced across devices through a small Fastify backend.

Three workspaces in one repo:

| Path | What | Notes |
|---|---|---|
| root | Frontend app (Vue 3 + Vite + Pinia + Tauri) | The main package; content, rendering, stores all under `src/` |
| `server/` | Optional account-sync backend (Fastify + JWT, PostgreSQL / PGlite) | Only needed for login + cross-device sync |
| `src-tauri/` | Rust shell for desktop / mobile packaging | Rust code is separate; frontend builds to `dist/` |

Code comments, user-facing strings, and commit messages are written in Chinese — match that style.

## Commands

Frontend (root):

```bash
npm run dev                # Vite dev server on 5173; /api proxies to 127.0.0.1:3000
npm run build              # production build (runs build-search-index first)
npm test                   # Vitest run (node env, tests/**/*.test.js)
npx vitest run tests/useKatex.test.js   # single test file
npm run lint               # ESLint on src+tests, --max-warnings 0 (CI gates on this)
npm run lint:fix
npm run validate:content   # JSON-Schema check of content data — MUST pass after content edits
npm run format             # Prettier on src/tests
ANALYZE=1 npm run build    # emit dist/stats.html bundle visualizer
npm run tauri:dev / tauri:build
```

Backend (`server/`), run from that directory:

```bash
cp .env.example .env       # first time; then edit JWT_SECRET
npm run dev                # node --watch; PGlite (file DB under server/data/) when no DATABASE_URL
npm test                   # node --test (test/sync-core.test.js)
node --env-file=.env src/index.js   # production-style start
```

CI (`.github/workflows/ci.yml`) runs on every push to `main`: content validation → lint → vitest → `vite build`, plus `cargo check` for Tauri and backend tests. Two extra jobs deploy frontend (zero-downtime rsync) and backend after CI passes.

## How content works (the core model)

Content pages are **data, not templates**. To add a page you do NOT write a Vue component:

1. Create a page module under `src/content/<subject>/<unit>/NN-<name>.js`. It `export default`s a page object whose entries are blocks.
2. Register it in the subject's `site.js` file array (`src/content/site.js` = math, `chinese/site.js`, `computer/site.js`). Units carry `phase`, tests are flagged `isTest: true`, sprint units `sprint: true`.
3. Run `npm run validate:content` — CI rejects invalid content. Known strict rule: formula lines must not end with a lone trailing `\`.

- Block shape is governed by `schema/content-schema.json` (~14 types: knowledge / formula / example / quiz / exam / error-focus / mindmap / table / tip / warning / objectives / strategy / geometry …).
- `UnitView.vue` resolves route param → subject/unit/fileIndex → dynamically imports the content file, so **each content file becomes its own lazy chunk** (~200 pages). Keep content files self-contained; every page file is shipped separately.
- Every page has a set of Chinese `files` names in `site.js`; the home page, sidebar, and TOC are all derived from these site configs (via `src/content/index.js` → `SUBJECTS` / `getSubjectConfig`).
- The full-text search index is generated by `scripts/build-search-index.mjs` into `public/search-index.json`. `npm run build` runs it automatically; after adding content, run it manually (`node scripts/build-search-index.mjs`) to keep dev search fresh.

## Rendering & heavy dependencies

`BlockRenderer.vue` dispatches on block `type` to `src/components/blocks/*.vue`. Heavy libraries are loaded lazily on purpose and must stay that way (bundle discipline matters here — main chunk was slimmed from ~1MB to 35KB):

- KaTeX — formulas (`FormulaCard` etc.), via `useKatex` composable.
- Mermaid — mind maps/flowcharts, loaded async (`useMermaid`).
- JSXGraph — `GeometryBlock`/`JsxGraphBoard`, ~1MB, dynamically imported only.
- GeoGebra — self-hosted offline assets under `public/vendor` (no external CDN), used in `GeoGebraPlayground.vue`.

`vite.config.js` `manualChunks` splits vendor chunks and sets `chunkSizeWarningLimit: 1000`; don't force big libs into the main bundle.

## Data layer & stores

- Single IndexedDB database **`study_game_db` (v5)**, opened/wrapped by `src/stores/studyDb.js` (a Pinia store of CRUD actions). Stores: `study_log`, `daily_stats`, `page_progress`, `error_book`, `notes`, `bookmarks`, `user_progress`.
- **Schema-evolution rule:** to add/rename a store, bump `DB_VERSION` and add an `onupgradeneeded` block keyed on `oldVersion` — keep `DB_NAME` unchanged for compatibility (v5 deleted the legacy `achievements` store; historic upgrade blocks are left in place for old installs).
- Feature composables (`useNotes`, `useBookmarks`, `useSpacedReview`, `usePomodoro`, `useTheme`, …) are thin modules that call `studyDb` actions.
- `src/stores/progress.js` keeps the `subject→unit→fileIndex` completion map and persists it into the `user_progress` store (`'main'` row). It also one-time migrates legacy localStorage progress.
- Gamification (XP / achievements / streaks / heatmap / 打卡) was **deliberately removed in v0.2.0**. Remaining comments mentioning XP/打卡 are stale — do not resurrect that feature or those fields; treat game concepts as removed.
- `src/types/*.d.ts` are **documentation only** — never type-checked (no `vue-tsc` script; tsconfig excludes plain `.js`, code is JS, not TS). Don't treat them as an enforced contract.

### Known design tensions (avoid adding to them)

- **Two progress models coexist:** `page_progress.visited` (auto-written per page visit; drives the dashboard) vs `user_progress.completed` (manual toggle; drives home/unit UI). They can disagree and test pages are double-keyed. Don't introduce a third tracker; ideally converge these before building new progress features.
- **Sync keys:** `error_book` / `study_log` are synced by their local auto-increment numeric `id`, which is **not collision-safe across devices** (two devices each start at 1 and LWW-overwrite). For anything new you sync, prefer UUID / semantic keys (notes & bookmarks already key by `pageKey`, which is safe).
- **Deletes don't propagate:** local deletes just remove the IndexedDB row; the sync layer only *applies* tombstones pulled from the server, never writes them. Don't assume a deletion reaches other devices.

## Auth & sync architecture

- **Every route except `/login` requires login** (`src/router/index.js` guard); `/admin` additionally requires `role === 'admin'`. Toggle complete / visit tracking etc. happen only while logged in.
- Tokens (`access` + `refresh`) persist to localStorage via the `auth` Pinia store. `sync/api.js` attaches Bearer, auto-refreshes once on 401.
- Backend routes: `/api/auth/*` (register/login/refresh/me), `/api/sync` (one push+pull call, LWW conflict resolution over `sync_items`), `/api/admin/*`. Passwords hashed with Argon2id. DB is PostgreSQL when `DATABASE_URL` is set, otherwise embedded PGlite files.
- **Sync engine principle: IndexedDB is the single source of truth; the network is only a channel.** `src/sync/engine.js` collects all local rows with `updatedAt`, pushes them, pulls changes since a cursor, applies (tombstones or overwrite-by-server-timestamp). It is wired only from `App.vue` (manual button, on mount, 5-min interval) — not from individual stores.
- Backend config is env-driven: `JWT_SECRET`, `ALLOWED_ORIGIN`, `DATABASE_URL` (see `server/.env.example`). Production must set `JWT_SECRET`; never commit `server/.env`. The dev fallback secret is insecure by design — don't rely on it outside local dev.

## Conventions worth knowing

- Router is **hash mode** and Vite `base: './'` — required for Tauri's local-file protocol. Don't switch to history mode.
- `validate:content` + `lint --max-warnings 0` are hard CI gates; run them locally before committing.
- Content/UI is Chinese; keep new content blocks, site entries, and comments in the same style.
- `docs/COMPONENTS.md` and `MIGRATION-README.md` describe component inventory and the migration history — useful for naming and intent.
- There is a low-code editor at the `/editor` route for authoring content blocks, and content can be exported to data files from it.
